## Overlap resolution rules

1. Discovery precedes orchestration when boundaries are unknown. For repository tasks, `repository-intelligence` supplies the architecture/ownership map; for documents, research, data, or other work, the parent supplies equivalent resource boundaries before parallelization.
2. Unknown-defect discovery precedes causal diagnosis: `bug-finder` hunts and proves concrete failures; `debugging-investigator` takes over only when a known symptom needs its causal chain established.
3. Diagnosis precedes migration only when the cause is unknown: `debugging-investigator` isolates; `codebase-evolution-controller` changes versions or contracts.
4. Builders own focused verification for their change. `verification-and-release` evaluates the integrated evidence and release controls.
5. Design direction, reference reconstruction, and implementation are separate decisions. Use the smallest set needed and make handoffs explicit.
6. Mobile selection is not implementation. A chosen platform builder may challenge an invalid assumption but must not reopen the decision without new evidence.
7. Review/refactor, performance, and TypeScript quality skills may inspect immediately but must stop at AWAITING_APPROVAL before broad edits or policy changes; later approval covers only the proposed batch/stage.
8. `codebase-improvement-planner` owns open-ended “what should we improve?” discovery. Once it selects a concrete TypeScript quality, migration, bottleneck, bug, refactor, or platform task, the specialist skill owns execution details.
9. `typescript-quality-enforcer` owns recurring TypeScript/JavaScript type-evidence and deterministic lint policy; a specific toolchain migration, runtime bug, or architectural dependency-seam refactor hands off rather than being disguised as lint cleanup.
10. `content-provenance-hygiene` owns inspection and authorized deterministic metadata sanitation. Substantive rewriting, generic image editing, service implementation, or detector-evasion goals are not absorbed into provenance cleanup.
11. `completion-proof` owns completion discipline, not the domain decision. It may wrap an already-scoped specialist task, but it cannot cross that specialist's approval/safety stop or replace `verification-and-release` as the final ship decision.
12. A defined diff/PR routes to `review-and-refactor-code`, even when the review may discover bugs; open-ended unknown-bug hunting routes to `bug-finder`.
13. `toolchain-preflight` owns only the local execution path. It exits when one supported invocation reaches the actual task, then hands application behavior, migrations, implementation, or release judgment to the owning specialist.
14. `security-review` owns security-first code review. Ordinary correctness/maintainability review stays with `review-and-refactor-code`; supply-chain/version transitions stay with `codebase-evolution-controller`.
15. `rust-engineering` owns bounded Rust implementation, including local ports with a decided target. Review-only Rust work stays with `review-and-refactor-code` and its Rust reference; service/edition/toolchain transitions stay with `codebase-evolution-controller`, which can hand over a bounded Rust implementation stage. A Rust dependency mention alone is not an implementation trigger.
16. Kotlin, Python, C++, Swift, and Go implementation follow the same owner boundary as Rust. Match the changed contract in a mixed repository; do not activate a language specialist just because a build tool, helper, or unchanged caller uses it. The review skill owns its language checklists, platform builders retain feature integration, and evolution stages pass their compatibility and rollback constraints to any language implementation owner.
